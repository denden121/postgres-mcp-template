# Подключение своей базы и добавление операции

1. Создайте репозиторий из шаблона. Для существующей БД **не запускайте** SQL из db/:
   эти скрипты создают демонстрационную базу и роли.
2. Создайте отдельную LOGIN-роль без прав на таблицы, создание объектов и смену роли.
   Следуйте принципу минимальных прав; не используйте postgres в DATABASE_URL.
3. Владелец таблиц создаёт отдельную функцию для каждой бизнес-операции.
   Пример — api.sales_summary в db/migrations/002_shop.sql. SECURITY DEFINER требует
   доверенного NOLOGIN-владельца, фиксированного search_path, отзыва EXECUTE у PUBLIC
   и явного GRANT EXECUTE нужной роли. Проверьте ограничения и внутри функции.
4. Добавьте модуль в src/postgres_mcp/operations с описанием инструмента,
   типизированными аргументами и проверками диапазонов. Используйте sales.py как пример.
5. Зарегистрируйте инструмент при запуске сервера. Включите его фиксированный запрос
   в используемый database.py реестр. Имена таблиц, SQL и имена функций от агента
   принимать нельзя. Все значения передавайте параметрами %s.
6. Добавьте тесты результата, прав БД и плохих аргументов. Новая операция должна
   быть явно разрешена в конфигурации harness, если используется строгий пример.
7. Укажите DATABASE_URL в локальном .env и подключите MCP-клиент по stdio.

Универсальная часть шаблона — подключение и инфраструктура исполнения.
Бизнес-схема, SQL и разрешения адаптируются разработчиком; автоматического
доступа ко всем таблицам и универсального execute_sql здесь намеренно нет.

## Граница безопасности

Права PostgreSQL ограничивают доступ к бизнес-данным, но не запрещают SELECT 1
или все системные каталоги. Пользователь с Docker и административными паролями
может обойти коннектор. Harness ограничивает инструменты агента, а не полномочия
самого пользователя ОС. Для сильной изоляции разделяйте окружения агента и БД.
Пример OpenCode закрывает все инструменты кроме двух MCP-вызовов и question;
Code Mode отключён, чтобы инструменты вызывались напрямую.
Проверьте применённые политики в своей версии OpenCode; глобальные политики имеют
более высокий приоритет. Пример рассчитан на OpenCode 2.2.6.

## Особенности демонстрационной схемы

Выручка — сумма quantity * unit_price по paid-заказам за дату заказа, не дата платежа.
CHECK и FK не обеспечивают совпадение суммы платежа с позициями заказа, отсутствие
длинных циклов категорий или наличие позиции у каждого заказа. Это отдельные
бизнес-правила, которые следует реализовать в приложении/функциях при расширении.
